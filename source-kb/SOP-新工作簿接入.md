# 新工作簿接入 SOP（方法论，非通用工具）

> 本文档沉淀的是**流程与纪律**，不是可复用代码。每份新工作簿的结构、口径、残留情况都不同，
> 没有一次写好永久通用的转换器——每份按本 SOP 走一遍，产出当次的抽取脚本。
> 参考实现：`gen-real.py`（镇龙东F10，2026-09，含 95 项断言的完整范例）。

## 流程总览（约半天～一天/份）

```
人工读全表定口径 → 写抽取脚本(坐标+断言) → 生成 md → 双层反向核查
→ 分层灌库(摘要建图/明细只检索) → 实测三场景 → 提交
```

### 第 1 步：读全表，先甄别再动手（人工，最关键的一步）

- openpyxl 逐 sheet 打印全部单元格，**每张表判断：真实数据 / 其他项目模板残留 / 空模板 / 重复口径**
- 残留表**不是整表丢弃**——可能表头是残留、数据列是活的（镇龙东F10 的审核表即此情况），逐格甄别
- 记录每个"能不能用"的判断和依据，写进生成文档的来源声明

### 第 2 步：定口径（人工）

- 明确哪些数字进知识库、哪些推导值可用（推导必须写公式进文档，如"红线=8%+1.3%+0.837%"）
- 数值铁律：**没实测的不作数字承诺**；工作簿没算的（如现金流）宁可标缺失，不编

### 第 3 步：写抽取脚本（坐标 + 断言，参考 gen-real.py 结构）

- 数字一律"坐标直读"，**禁止手抄**进模板
- 关键值硬断言（`near()`）；分项加总 = 合计的断言必须有
- 字符串清洗（单元格内嵌换行会撕裂 md 表格——cell() 里压平）
- 文档结构按"这个库要回答什么问题"设计：摘要级（建图谱）/ 全量明细（只检索）分层
- 每份文档标题带项目全称+简称（防跨项目检索歧义）

### 第 4 步：双层反向核查（脚本）

- `verify-real.py` 式：从生成的 md **反向解析数字**与 xlsx 原单元格比对（与生成断言相互独立）
- `verify-full.py` 式：源→文档逐格覆盖率 + 文档→源溯源 + WeKnora chunk 闭环（--api）
- 覆盖率要求：摘要级表 100%，明细表按设计豁免并明示"以源表为准"

### 第 5 步：分层灌库

- `upload.mjs --src <目录>`；明细类文档文件名含"全量明细/主要材料与分包价格"自动跳过图谱
- 全量明细的 chunk 可能出现孤立表格尾行（auto 分块切边）——源 md 游程扫描归零即可，非缺陷

### 第 6 步：实测三场景（真链路）

- 高权角色推演（引擎数字逐位）/ 低权角色问库外（正确拒答）/ 口径查询（能答）
- 实测用脚本：`role-live-check.mjs` / `safety-retry.mjs`（改账号与问题复用）

## 历史踩坑速查（详因见项目记忆 zhenlongdong-f10-*）

| 坑 | 一句话 |
|---|---|
| 库名关键词授权 | 已改显式 kbIds 矩阵；新库默认不可见，加矩阵才可见 |
| WebUI/API 配置假成功 | 配置走 PUT /initialization/config 的 nodeExtract；改完回读验证 |
| JSON 字段名 | 对 Go 后端必须按 struct tag（file_types 非 fileTypes），camelCase 静默丢弃 |
| 终端内联中文 | GBK 乱码入库；带中文的写操作一律 python 文件载荷（utf-8） |
| dashscope 5xx 窗口 | 非限流；等窗口过去重试，与并发无关 |
| finalizing 卡住 | 容器重启丢 asynq 任务，手动 POST /knowledge/{id}/reparse |
| engine-data 换数据源 | 同步 grep smoke/e2e 里的项目名与数字断言 |
| 内置快速问答 | kb_selection_mode=all 全库检索，不分配给角色 |
