# 利润推演引擎 MCP 服务 v2（RAG 供数 · C 路线）

## 架构（负责人决策 2026-09-02）

```
用户提问 → Agent 从多源知识库现场检索基线与常量
   ├─ 合同资料：中标合同价
   ├─ 成本月报：目标成本 / 累计实际成本 / 实际利润率 / 成本完成度
   ├─ 综合月报：形象进度 / 滞后节点 / 风险总数 / 红色风险 / 回款率
   ├─ 制度文件：利润率红线 16.66% / 钢筋成本份额 18%
   └─ 现金流库：本期现金流结余 / 临界预警线 200 万
        ↓
run_scenario(period?, project, baseline✱, globals✱, factors)  ← 缺字段硬拒绝
        ↓
引擎确定性计算（engine.mjs 单源）→ 结果回灌 Agent → 总结输出
```

✱ 必填。任一字段缺失，zod schema 直接拒绝并列出缺失清单，模型必须回知识库补检索——这是"问时现抽"架构下防"静默编数"的主保险。

## 与 PRD 附录 D 的偏离（记录在案）

附录 D 原签名 `run_scenario(project_id+6因子)` 假设引擎自持基线数据。本版本改为 **AI 从 RAG 检索供数**（含 baseline 15 项与 globals 3 项），系负责人 2026-09-02 拍板的架构决策："这正是我建立 RAG 的理由"。`get_baseline` / `get_current_status` 两工具随之移除（其内置数据路径与该架构矛盾）。

## 已知取舍（写明不藏）

- **取数准确性由检索层决定**，逐问方差存在（实测：同一问题一次成功、一次凑不齐字段主动放弃；改进后稳定）。缓解：schema 必填硬拒 + 智能体 system prompt 字段→知识库地图 + 模板化表格文档 + 温度 0.1。
- **跨文档聚合字段**（累计成本 = Σ结算）仍依赖源文档直接给出结论值，引擎不做聚合。
- **M1 评测（20 题逐位）是该架构的主护栏**；绿横幅语义 = "引擎参与了计算"，不含"输入数据经人工放行"。
- 引擎内置常量（engine-data.mjs）不再作为计算输入，仅存于网关对账拒收时的兜底出数（PRD §7.3 原文）。
